# Release upgrades

Designed, not built: [release upgrades](../releases.md) implement R1.31 with releases installed side by side under `releases/<version>/`, each verified against its sha256 before it can run.
A copy-scoped release pin selects the release for new work in that copy only; the shared launcher resolves the copy before execution, and standalone Directors set it with `guildhall release use`, managed Directors take it from `managed.toml` by approved rollout, and either route records a `release-pin` store event, so no upgrade feature needs a Steward.
A managed pin is applied only after `guildhall config reload` authorizes its revision, consistent with the [optional Steward](optional-steward.md) observed-untrusted rule.
A fixed PATH launcher runs the pinned release and never falls back to another one, except for `guildhall release` commands, so a broken pin can always be repaired.
Tasks record their release at creation and every later step dispatches through the launcher using the owning store and task identity, so a pin change reaches new tasks only and rollback is just moving that copy's pin back. Artisan launches and resumes retain Herdr's plain `guildhall` command; the launcher selects the recorded release and replaces inherited `GUILDHALL_RELEASE` with that version, without changing Herdr.
The Steward tells a Director about a new release by command, not message: after `config reload` it runs `guildhall director reload` over SSH, which restarts the Director's agent session at its next step boundary and never mid-step.
This makes `director reload` a second fixed remote command, further narrowing D12 as the optional Steward decision did for `config reload`.
`guildhall release prune` runs after every pin change and keeps the newest three installed releases by install time plus protected releases, with no retention setting. Protection includes every pin, rollback target and running or resumable task across all copies registered with the shared installation home; unreadable or inconsistent copy state blocks deletion, and reference creation is serialized with pruning. Each removal is a store event.
Keeping protected releases beyond the limit was chosen over a strict count because deleting a release a task still needs would strand that task.
