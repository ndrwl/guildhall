# `internal/cli`

## Contract

`spend report` follows the [recorded spend contract](../spend.md).
`clerk guild|decisions|task|inspect|queue` follows the [Clerk contract](clerk.md): read-only plain-text answers over the copy from `--copy`, which must already be marked, or copy discovery.
`web [--copy <dir>]` follows the [task pages contract](web.md): over the copy Clerk's way selects it, it serves the pages at the config's `[web]` address, bound through `App.WebListen` (nil is `web.Listen`, tailnet only), until a signal; no `[web]` table, a config that does not load and a refused address exit 1, an argument exits 2.
The Director role's `watch` hook serves the same pages for each session with a `[web]` table, closed by `runSession` before the session's end is recorded, and writes `state/web.json`, the serving record of that session's state (`serving`, or `failed to bind` with the reason); `director status`'s `web` object reads it for the running session, and `director start`'s preflight names the address in a `web` line.
`StewardDecisionOptions` exports the Steward's rollout approval options for the page's option-meanings table.
`ci log` follows the [CI logs contract](../ci-logs.md): over the copy from `--copy` or copy discovery, it reads the store read-only, takes no task lock, finds the job among the `logs` of the task's failed validate results, each checked against its recorded digest, and serves it through `cilog.Get` with `config.CILogLimit`, reading through `App.Forge` when it is an `interp.CheckLogReader` and `forge.GitHub` otherwise; `ci_test.go` pins the limit reaching validate and `task files` not listing the cache, serving from the cache with no forge call by job and by check name while the test holds the task lock, discovery from the copy, no copy found under `state/` without `--copy`, `--tail`, `--out`, a fetch after pruning, exit 2 for an unrecorded job, a commit status, bad arguments and no copy, and exit 1 for an expired log, with its line naming the result, and a forbidden one; written with the implementation, not red first.
`TestSpendReportRecordedUsage` and `TestSpendReportRejectsInvalidInput` were written before implementation and failed to compile because `spendReport` did not exist; they then passed with the command implemented.
The additional `TestSpendReportMetadataFiltersAndMalformedEvidence`, `TestSpendReportRetriesAggregateWithoutTranscriptReads` and `TestSpendReportCopyAndHelp` cases were added after implementation and passed on their first run; they pin manifest identity, missing and malformed evidence, inclusive start times, repository/task filtering, environment copy selection and help against real fixture stores.
`TestSpendReportMetadataFiltersAndMalformedEvidence` also checks attribution from the published `prompt/manifest.json`; `TestSpendReportScansReceiptsOnlyOnceWhenFiltered` bounds receipt scans, and `TestSpendReportStartIndexSeparatesAttemptIdentities` covers start-receipt identity and legacy receipts.

Owned `artisan start --timeout` is a result-wait budget beginning after worker startup and recorded containment, not a budget for acquiring ownership.
`App.AdvanceContext`, when set, supplies task advances' interrupt subscription; nil uses `signal.NotifyContext`.
The interrupted-launch integration test uses the real subscription and releases its held lock only when that context is cancelled, not after a sleep.
The [timing policy](../test-timing.md) and [regression evidence](../evidence/ci-timing-flakes-2026-10-26.md) cover immediate result expiry, pre-start stop proof and deterministic watcher ordering.

Task admission and advance require a configured runtime for each Artisan stage, through its effective profile (`workflow.EffectiveProfile`): the profile it names, else its role profile, the copy's own or the [shipped](../configuration.md#profiles) one, resolved at use and never written into the effective workflow, so the task binds the bare definition's digest; an Artisan step whose type has no role and that names no profile is refused.
A missing profile fails with exit 1 and an error naming the step and directing the user to set a profile on that step, without task-record mutations or launches.
`TestTaskNewBindsTheShippedWorkflows` pins `task new` on `default` and `--kind bug`, with no `[profile.*]` and with the role profiles declared: each binds the shipped revision exactly and records no approval.
`TestExplicitProfileChangesTheDigest` checks a profile written into a step changes the digest and, on the review, is still a weakening the authority refuses, and `TestTaskNewGuildmasterReviewGetsNoDefault` that a Guildmaster review resolves no profile.

`task new --kind feature|bug|hallmark` chooses the [task kind](../tasks.md#task-kinds), `feature` by default and `bug` for `--fixes` without `--kind`; `hallmark` is only ever chosen explicitly. A feature binds the repository's `workflow` setting, and a bug or hallmark its `[repository.kinds]` entry or the shipped workflow of the kind's name; the shipped definitions are `default`, `bug` and `hallmark`, in that order.
A workflow other than the repository's feature workflow takes only the `workflow_overrides` naming its own steps (`overridesFor`).
An unknown `--kind` is a usage error, and `task new --help` prints the usage with each kind's description to standard output and exits 0.
`workflow approve --config --repo` takes `--kind` to approve that kind's effective workflow, and refuses it without them as a usage error.
`task_kind_test.go` pins binding with no kind, `--kind bug`, `--fixes` alone and `--kind feature --fixes`, a kinds override that needs approval, a retry with another kind as a mutation conflict, the refusals of an unknown `--kind` and of a kinds table naming `feature` or an unknown kind, the help, and the Director's tasks skill copying each description; `TestWorkflowApprovalsList` and `TestWorkflowApproveShippedRevision` list `bug` and `hallmark` with source `release`.
`TestPruneRemovesAFinishedHallmarkWorktree` pins that prune retires a done hallmark task's worktree at the head its `finished` record names, with no merge record, and keeps it when the record names none.

Advance, `step done` and `step finish` resolve a task's workflow by its bound revision's name, not the repository's current `workflow` setting: the shipped definition of that name or `workflows/<name>.json`, with the repository's current overrides, refused with an error wrapping `interp.ErrRevision` and naming the bound workflow when its digest differs; a task bound while role profiles were written into the digest bound the legacy digest of that definition with every role step's profile defaulted (`workflow.ApplyProfileDefaults` with every role declared), which is accepted too and runs the defaulted definition ([decision](../decisions/role-profiles-outside-the-digest.md)).
`TestBoundWorkflowResolvesByName` pins resolution after the setting moves and the refusal after the file is edited or removed; `TestBoundWorkflowAcceptsTheLegacyDefaultedDigest` resolves the legacy and bare digests and refuses another, and `TestLegacyDefaultedTaskStillAdvances` starts a task bound to the legacy digest, takes its plan's result and reaches acceptance; `TestOpenTaskKeepsItsWorkflowWhenTheRepositorySwitches` advances, finishes and takes a result for a task after its repository moves to another workflow, and `TestOpenTaskStrandsWhenItsWorkflowFileIsEdited` refuses `task start` after the bound file is edited, launching nothing.
Explicit profiles whose adapter is `fake` are still accepted; there is no default-adapter remedy.
The original `adapter_admission_test.go` regressions reproduced silent admission and fake launch before implementation ([historical red evidence](../evidence/no-silent-fake-2026-10-26-red.txt)); the [historical green evidence](../evidence/no-silent-fake-2026-10-26-green.txt) records the initial fix, before admission was narrowed to named profiles only.
The current tests refuse task creation on a custom workflow whose refute step names no profile, asserting the custom-workflow remedy and unchanged real store bytes, and show that a legacy task's plan step with no profile, in a copy that declares no planner, runs under the shipped claude planner rather than any fake, which the test binary refuses before recording.

Commands, output and exit codes (README); doctor's process boundary, `App.LookPath` and `App.Output`: a missing tool is `exec.ErrNotFound`, output is stdout and stderr combined, a failing command is an error with its output, and context cancellation stops a hung command; see [doctor reports only what it checked](../decisions/doctor-reports-only-what-it-checked.md) for doctor's timeout policy.
The `store`, `messages`, `task`, `decide`, `workflow approve` / `workflow approvals` and `steward rollout` commands, including the read-only task inspection reads `task timeline` (with findings and rulings) and `task files`, `task finding rule` and `task review --full` (`docs/store.md`, `docs/messaging.md`, `docs/tasks.md`, `docs/decisions-cli.md`, `docs/configuration.md`, `docs/steward.md`); task acceptance refuses undeclared profiles in the effective workflow before opening or writing the store, and refuses an unauthorized effective workflow through `workflow.Authority.Admit` over the shipped definitions and the store's approvals before writing; `workflow approve --config --repo` approves a repository's effective workflow; see `docs/tasks.md` for task acceptance and retry contracts.

`artisan start` without `--herdr-session`, `artisan stop`, `artisan status` and `artisan resume` are [owned attempt commands](../artisan.md#commands) over [`internal/launch`](launch.md); `artisan start` with `--herdr-session` is the [tab mode](../adapters.md#running-an-attempt).
Workflow and quality launches lazily resolve the configured `herdr_session` through the production Herdr client and pass that terminal and `ReportAgent` into `launch.Process`, which creates a new labelled workspace per attempt without focus ([workflow workspaces](../artisan.md#workflow-artisan-workspaces)).
The Artisan workspace host serializes creation and optional ordering under an account-private per-session presentation lock, so successful ordering preserves launch order across concurrent tasks.
It reads the Director's existing pane binding without changing the store, verifies that tab and pane live, and journals only response-created workspace ids and labels under the state directory before attempting one move.
The complete optional ordering operation has a child context capped at two seconds and shortened to reserve ten seconds of the caller's startup deadline; insufficient remaining budget skips ordering.
Ordering and journal failures warn on stderr and return the created workspace successfully; no task record, launch result, ownership or lifecycle changes.
`artisan_order_test.go` covers journal binding, uncertain-move non-retry, corruption refusal and warning-only creation with a busy lock or missing Director store; these tests were added after implementation and passed on their first run.
`artisan_order_lab_test.go` exercises the production host and socket boundary in the guarded named-session lab ([evidence](../evidence/artisan-child-workspaces-2026-10-26-live.txt)).
No session retains hidden mode; result-only advances and cancellation do not resolve Herdr.
The internal owned `artisan start --pane-launch` bridge detaches the same start invocation without that flag and streams `launcher.log`; it never forwards terminal closure as a stop request.
Its internal `--workspace-close-after <duration>` flag, refused without `--pane-launch` and also dropped from the detached invocation, is the effective `artisan_workspace_close_after` its finish line states (`launch.FinishLine`); `artisan_test.go` and `labels_test.go` pin the flag and the line.
The opt-in `TestWorkflowArtisanHerdrLab` and ordinary CI's pane stand-in are described in the [launch contract](launch.md#tests).
The `artisan` verbs follow the [role grammar](../decisions/cli-role-grammar.md): help lists every one, and `artisan run`, the pre-release name of `start`, is a usage error that names `artisan start`; their repository flag is `--repo`, and the pre-release `--repository` is a usage error that names `--repo`.
`artisan harness inventory|kill-owned|probe --lab` is the lab's [test tooling](../artisan.md#harness), refused without `--lab`.
`fake-artisan` is `fake.Main` and `claude-artisan` is `claude.Main`; `artisan start` builds its command from [`runtimes.Lookup`](adapter-runtimes.md) and refuses an `--adapter` that `runtimes.Names` does not list with a usage error naming it and the list; owned it takes `fake` or `claude`, and tab mode only `fake`; owned, `--copy` and `--profile` are put on the adapter spec for configuration lookup and `--model` and `--effort` as its `Settings`, a setting the runtime refuses being exit 1 before the attempt is owned, and in tab mode `--profile`, `--model` and `--effort` are a usage error.
`--allow-tool` is a usage error in both modes and in `claude-artisan`.

`task start`, `step done` and `step retry` ([running a task](../running.md)) run one `interp.Engine` advance over `storeRecords`, the Director config and the state directory, under the task's lock, launching through `launch.Process`, given the copy when the advance runs from one so each launcher advances its task ([the watcher](../running.md#the-watcher)), writing what the task waits for to `next.json` beside the lock, with the task lock and every store open waiting `config.LockWait`, and `Engine.StallInterval` from `config.StallInterval`, also passed to `launch.Process` so each launcher sends `worker-stalled` from its heartbeat through the store and the wake, and `Engine.ChecksRefresh` from `config.ChecksRefresh`, and `Engine.CILogLimit` from `config.CILogLimit`, publishing and merging through `App.Forge`, which is `forge.GitHub` when nil, and making each task's working directory a worktree through `App.Workspaces`, which is `git.Program` when nil, with `Engine.Base` the task's base from `git.Program.Base` over the repository's configured `path` and branch `guildhall/<task>` and `Engine.Rebases` `git.Program` over the same `path`, whatever `App.Workspaces` is, on a context an interrupt cancels, so an interrupted advance returns and releases the task lock; `task start`, `step done` and `step retry` refuse a repository the config does not list (`config.ListedRepository`) before anything else, as `step finish` does before it reads its outputs, and the advance starts every attempt under `Engine.Caps` from `config.GuardRails` ([guard rails](../director.md#guard-rails)); `task new` and `workflow approve --repo` find the repository the same way, `task new` and the advance's `Engine.CheckSettings` enforce [runtime settings](../adapters.md#runtime-settings) at their respective admission points, and `messages send` checks the envelope's repository against the copy's config or `--config`; `step done` refuses a result path other than the attempt's own and a result `adapter.ReadResult` refuses before calling the engine; `step retry` feeds `attempt-retried` with its `--reason`.
`step finish` ([running a task](../running.md#step-finish)) is the Director's verb for a [Director stage](../interpreter.md#director-stages): it refuses a step the repository's effective workflow does not run by the `director`, an output port its kind does not declare, an attempt that is not the step's latest, already finished or not `interp.HandedToDirector`, then, under the task's lock, copies each output into the working directory as `<port><ext>`, writes the result with `adapter.WriteResult` and feeds `attempt-result`; the prompter renders a Director stage with `roles/director.md` or the config's `[director] role`.
`storeRecords` is the production `interp.Records` and `interp.Outbox`: it opens the store for each record operation, waiting at most its wait for the lock, `storeWait` (`config.DefaultLockWait`, 30 seconds) when unset and the copy's `lock_wait` in an advance, joins each result with the close error, and satisfies `interptest.RunRecordsContract` and, through its `Send`, `messagingtest.RunMailboxContract` ([seams](../interpreter.md#seams)).
`quality judge --repo <id> --review <n> <task>` and `quality judged --repo <id> --task <id> --attempt <n>` need a copy, `--copy` or the copy found from the current directory, for its `quality/` directory, and run [`quality.Judge`](quality.md) `Start` and `Take` under the task's lock with the copy's guard rails and pause hold, a `launch.Process` launcher over the copy, an unknown historical builder family for both profiled and unprofiled builds (never classified as separate-family), and the role `roles/judge.md` from the copy's baseline, else the release's, or a judge profile's own `role`; each prints its result as one JSON line, a start the pause holds prints `{"wait":"paused"}`, and the Director is woken for what they sent once the lock is released, as an advance does.
`quality agreement [--repo <id>]` prints `quality.Agreement` over the config's repositories, or the one named, as one JSON line.

`review check <outcome-file> [--previous <previous-outcome-file>]` is the reviewer's self-check before it finishes, required by the [`guildhall-review`](../../skills/guildhall-review/SKILL.md) skill and granted to the shipped reviewer profile: it parses the file with `workflow.ParseReviewOutcome`, as intake's `checkPort` does, and with `--previous` also parses that file and runs `(ReviewOutcome).Covers`, the coverage check intake's `checkOutcome` runs, so there is no second validator.
It needs no store, copy or config and does not check `BoundTo`, for which the reviewer has no file of the attempt's revisions.
A valid outcome prints `ok` and exits 0; a refused or unreadable one writes the whole error, every problem `Validate` joined, to stderr and exits 1; a usage error exits 2.
`TestReviewCheckRefusesWhatIntakeRefuses`, the d12 and d27 outcomes intake refused, and the other `TestReviewCheck*` cases were written red first and failed with `unknown command "review"`; `TestReviewOutcomeCovers` failed to compile before `Covers` existed.
`task new --fixes <repo>/<task>` records the task's `Fixes`; a value that is not `<repository>/<task>` is a usage error.

`task new --priority <level>` records the new task's [priority](../tasks.md#priority) with the mutation `priority:<repo>:<task>:1` after creating it, and `task priority <task> <level>` records the next change as `priority:<repo>:<task>:<n>`, printing its receipt; a level already in force prints the receipt that set it. A level is `p0`–`p5`, `0`–`5` or its word, and anything else is a usage error. `task list` and `task show` print each task through a view that adds `priority`, `p3` when none was set, and `task timeline` adds `priority` and `priority_changes`.
`task list --workflow <name>` lists only the tasks bound to that workflow name and `--open` only open tasks, alone or together and with or without `--repo`, with output otherwise unchanged; they are a usage error on other task subcommands. The Director checks `task list --workflow <name> --open --json` before deleting `workflows/<name>.json`; nothing refuses the deletion. `TestTaskListByWorkflow` covers the filters.

`task context add|list` ([task context](../tasks.md#task-context)) take `--store`, or `--copy` / copy discovery, `--repo` and the task as a positional argument, in any order; `add` takes exactly one of `--text` and `--file` (not `-`) and records with the mutation `task-context:<repo>:<task>:<sha256 of the text>`, so a rerun prints the original receipt, and `list` requires `--json` and opens the store read-only; any other flag, a missing or extra argument, both or neither of `--text` and `--file` are usage errors (exit 2). `task show` adds `context` and `task timeline` adds `context`, each entry with `added_at`, and `store doctor` counts `task contexts` per repository. `TestTaskContextAddAndList`, `TestTaskContextReadsReadOnly` and `TestTaskContextRefusals` cover them.
`task link add|remove|list` ([task links](../tasks.md#task-links)) take `--store`, or `--copy` / copy discovery, `--repo` and the task as a positional argument, in any order; `add` and `remove` take `--document <repo>/<task>/<name>`, three ids naming one recorded document, and exactly one of `--text` and `--file` (not `-`), and record with the mutation `task-link:<repo>:<task>:<op>:<src repo>:<src task>:<name>:<prior>`, so a rerun while its record is the document's latest prints the original receipt; `add` also takes `--state` (or the copy's) and refuses, with exit 1, a document whose file under `<state>/documents` is missing or does not match its recorded digest; `list` requires `--json` and opens the store read-only; any other flag, a missing or extra argument, a malformed `--document`, both or neither of `--text` and `--file` are usage errors (exit 2), and a store refusal exits 1 writing nothing. `task show` and `task timeline` add `links`, every record with `added_at`, and `store doctor` counts `task links` per repository. `TestTaskLinkAddRemoveList`, `TestTaskLinkReadsReadOnly` and `TestTaskLinkRefusals` cover them.
`task override set|unset|list` ([task overrides](../tasks.md#task-overrides)) take `--store`, or `--copy` / copy discovery, `--repo` and the task as a positional argument, in any order; `set` and `unset` take `--key` and `--text`, and record with the mutation `task-override:<repo>:<task>:<op>:<key>:<prior>` (a key with characters a mutation id cannot hold is replaced by its sha256), so a rerun while its record is the key's latest prints the original receipt; `set` also takes `--value` and `--config` (or the copy's), loads the config before opening the store and, when `config.CheckTaskOverride` refuses the key or value, prints its reason unchanged and exits 1 writing nothing; `unset` reads no config; `list` requires `--json` and opens the store read-only; any other flag, a missing or extra argument, a missing `--key`, `--text` or, on `set`, `--value` are usage errors (exit 2), and a store refusal exits 1 writing nothing. `store doctor` counts `task overrides` per repository. `TestTaskOverrideSetUnsetList` and `TestTaskOverrideRefusals` cover them.
`task new --override <key>=<value>` (repeatable) takes `--override-quote`, the Guildmaster's words, and checks every override with `config.CheckTaskOverride` before the store opens, so a refused one exits 1 and creates no task; after `CreateTask` (and the priority) it records each, in the order given, as `task override set` does, so a rerun replays each receipt; `--override` without `--override-quote`, the quote without an override, a value not `<key>=<value>` and a key given twice are usage errors (exit 2). `task show` takes optional `--config`, or the copy's, and adds `overrides`, the records in effect, and `skipped_overrides`, judged with `WithTaskOverrides` against that config, `null` without one or when it does not load, with a skipped merge-requires override among them, and `also_requires`, the merge requirements the overrides add, `null` likewise; `task timeline` adds `overrides`, every record with `added_at`; `director status` marks a task with an override in effect `overrides: true`. Every advance reads the task's override records under its lock and builds the engine on the task's effective config (`interp.ApplyTaskOverrides`), with the rails and `lock_wait` read from the copy's, and every merge gate reads the task's repository with its merge-requires overrides applied. `TestTaskShowOverrides`, `TestTaskNewOverride`, `TestDirectorStatusMarksOverrides`, `TestTaskOverridesReachTheArtisan`, `TestTaskOverridesReachValidate` and `TestTaskOverrideBindingWithoutOverrides` cover them.
`task depends add|remove` ([changing dependencies](../tasks.md#changing-dependencies)) take `--store`, or `--copy` / copy discovery, optional `--config`, `--repo`, `--reason`, the task and `<repo>/<dependency>` as positional arguments, in any order.
Each records with the mutation `task-dependency:<repo>:<task>:<op>:<dep repo>:<dep task>:<prior>`, hashed when over 128 bytes, so a rerun while its record is the dependency's latest prints the original receipt.

### Version

`guildhall version [--startup | --json] [--copy <dir>]` says which revision the binary is, which pull request it ends at and how far it is behind the repository's main ([decision](../decisions/version-from-build-info.md)).
`--copy` defaults to the copy found from the current directory, as for `director status`.
A positional argument, an unknown flag, and `--startup` with `--json` are usage errors (exit 2 with the usage text); stdout that cannot be written is exit 1; nothing else makes it exit non-zero.

**Build fields** come from the binary's build information through the `App.BuildInfo` seam, `debug.ReadBuildInfo` when nil: `vcs.revision` in full, `vcs.time`, `vcs.modified`, the Go version and `GOOS/GOARCH`, falling back to the running toolchain's for the last two.
`Version()` and its precedence (the release tag injected by the linker, then the module version, then `dev`) are unchanged, so `doctor` and the session record's `release` are unchanged.
A build with no `vcs.*` settings whose module version is a Go pseudo-version, such as `go install …@v0.0.0-20261030170552-650231703145`, takes `revision` (its 12 hex digits) and `time` (RFC 3339 UTC) from that version, with `modified` false, as the module proxy builds from a clean tree.
Any other build with no `vcs.*` settings, such as a tagged module-proxy install, `-buildvcs=false` or a tree without `.git`, has empty revision fields and shows the release only.

**Repository fields** are read only when a copy resolves and the build has a revision, from the copy's one repository whose `remote` names the binary's module path (`github.com/ndrwl/guildhall`), compared after dropping a URL scheme, a user, the colon of `git@host:path` and a trailing `.git` or `/`, in lower case.
No match, or more than one, gives no repository fields; there is no config key for it.

- *Latest merge:* the subject of the binary's revision in the repository's `path`; a trailing ` (#N)` is the pull request, and any other subject is none.
- *Task:* the task whose store document `tasks/<repo>/<task>/<step>/pull-request.json`, under the copy's `state/documents`, records that pull request number; none when this copy did not deliver it.
  No network or forge call is made.
- *Behind main:* `git rev-list --count --first-parent` and `git log --first-parent --format=%s` of `<revision>..refs/guildhall/version/main`, the remote's default branch fetched into that private ref with `git fetch --no-tags --no-write-fetch-head <remote> +HEAD:refs/guildhall/version/main`.
  Only plain `version` and `--startup` fetch; `--json` and `director status` read the ref as last fetched.
  An advance that leaves a task of this repository done with a `merge.json` document, a merge through Guildhall, also fetches it, with the same bound, recording the fetch the same way and ignoring any failure, before the `merged` message wakes the Director.
  A fetch that succeeds is recorded in `state/version-fetch.json` with its time; a fetch that fails leaves the ref as it was and the count says "as of" that recorded time, or "as of an earlier fetch" with no record; with no ref at all, behind main is omitted.
  The missing pull requests are the numbers ending the subjects behind, newest first; the text forms name at most ten, then "and N more".

Every git run goes through `App.VersionGit` (`VersionGit`: `Subject`, `FetchDefault` and `Behind`), `git.Program` with a five-second bound on each run when nil, so a hung remote costs at most five seconds.
Any repository failure, such as an unreadable path, an unknown revision or an unreachable remote, leaves those fields empty and never changes the exit code.

**Plain** prints `guildhall <version> <os>/<arch> <go version>`, then the lines it has: `revision: <revision> (<time>[, modified])`, `latest merge: #<pr>[ (task <id>)]` and `behind main: <n> merge[s][ (#<pr>, …)][ as of <time>]`.
**`--startup`** prints one line, `guildhall <first 8 of the revision, else the version>[ #<pr>][ <task>][ <commit date>][, modified]` with `, up to date with main` or `, <n> behind main[ (#<pr>, …)]` and any "as of", then at most one line `warning: ` joining with `; ` each of: behind main by one or more merges; modified, that is built with uncommitted or untracked files; a binary other than the one the current session's supervisor recorded, the session numbered by `GUILDHALL_SESSION` (`session.NumberEnv`) read read-only from the copy's store, compared by the sha256 of this binary's image with the session's `binary_sha256`, or by release for a session with none; and a binary that supervisor refused to move onto at the reload that started the session, naming its sha256 and the reason ([the supervisor's binary](../director.md#the-supervisors-binary)).
Warnings never change the exit code.
**`--json`** prints one object with every field present: `version`, `revision`, `time`, `modified`, `go_version`, `platform`, `pr` (number or null), `task` (string or null) and `behind_main` (null, or `count`, `missing_prs` in full and `as_of`, the recorded fetch time or `""`).

`director status --json` adds the same object as `version`, for the binary printing the feed, with no fetch, and, when its `behind_main` count is above 0, an `install` item at the end of `needs_me` ([status](../director.md#status)); the supervisor's in-flight snapshot does not compute either.
