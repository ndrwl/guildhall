and the adapter is not written. Open question 1 goes back to the Guildmaster.


1. Can a rules file deny by default?  NO
----------------------------------------

The rules language has three decisions, allow, prompt and forbidden, and
each one applies only to a command whose prefix matches a listed pattern.
A command that matches no rule gets no decision from the policy. It falls
through to the approval policy and the sandbox, and it runs.

`codex execpolicy check` with rules file a.rules:

  prefix_rule(pattern=["git", "status"], decision="allow")
  prefix_rule(pattern=["sh", "check.sh"], decision="allow")

  $ codex execpolicy check -r a.rules git status
  {"matchedRules":[{"prefixRuleMatch":{"matchedPrefix":["git","status"],"decision":"allow"}}],"decision":"allow"}
  $ codex execpolicy check -r a.rules ls
  {"matchedRules":[]}                      <- no decision at all for an unlisted command

A catch-all rule cannot be written:

  prefix_rule(pattern=["git", "status"], decision="allow")
  prefix_rule(pattern=[], decision="forbidden")

  $ codex execpolicy check -r b.rules ls
  Error: failed to parse policy at b.rules
      error: invalid pattern element: pattern cannot be empty

Real exec runs confirm it. With a.rules loaded as project rules:

  run 1, default approval policy (never):
    git status --short     exit 0  (allowed rule)
    sh check.sh            exit 0  (allowed rule)
    ls docs                exit 0  (NO rule: ran anyway)
    cat /etc/hostname      exit 0  (NO rule: ran anyway; outside the workdir)
    head -c 100 <attempt dir>/prompt.md   exit 0  (NO rule: ran; outside the workdir)

  run 2, -c approval_policy="on-request":
    python3 -c 'print(41+1)'   exit 0, output 42   (NO rule: ran anyway)
    go version                 exit 0              (NO rule: ran anyway)
    ls docs, cat /etc/hostname exit 0              (NO rule: ran anyway)

  -c approval_policy="untrusted" is refused by 0.163.0:
    Error: approval_policy = "untrusted" is no longer supported; remove this setting

So neither approval policy that 0.163.0 accepts turns "no matching rule" into
a refusal. The only way to approximate deny-by-default would be to enumerate
every program as `forbidden`, which is not an enforced allow-list.


2. Are the rules loaded and enforced at all?  YES, for listed prefixes
----------------------------------------------------------------------

Run 3 used this project rules file:

  prefix_rule(pattern=["git", "status"], decision="allow")
  prefix_rule(pattern=["sh", "check.sh"], decision="allow")
  prefix_rule(pattern=["python3"], decision="forbidden")
  prefix_rule(pattern=["go"], decision="prompt")

  python3 -c 'print(41+1)'  refused: "Policy rejected commands starting with `python3`"
  go version                refused: "approval required by policy, but AskForApproval is set to Never"
  ls docs                   exit 0   (no rule: ran)

The two refused commands produced NO item.started or item.completed event in
the --json stream. Only the agent's own text reports them (see run 3 below).
A decoder therefore cannot name a policy denial from the event stream alone.


3. Can exact rules such as Bash(sh check.sh) be expressed?  NO
--------------------------------------------------------------

prefix_rule is the only rule form, and it matches by prefix:

  $ codex execpolicy check -r a.rules sh check.sh extra
  {"matchedRules":[{"prefixRuleMatch":{"matchedPrefix":["sh","check.sh"],"decision":"allow"}}],"decision":"allow"}

An exact Guildhall rule would be widened to a prefix rule.


4. Network and reads outside the workdir
----------------------------------------

Network is off with sandbox_workspace_write.network_access=false:
  curl -sS -m 5 https://example.com -o /dev/null
  -> exit 6, "curl: (6) Could not resolve host: example.com"

Reads outside the workdir are allowed under workspace-write:
  cat /etc/hostname                    exit 0
  head -c 100 <attempt dir>/prompt.md  exit 0
so `guildhall review check` and the copy's store would be readable.

6. Not pinned by this spike
---------------------------

- Effort levels (minimal, low, medium, high, xhigh): only `low` was run.
- How exec chooses which rules file to load. The spike used project rules at
  <workdir>/.codex/rules/; codex exec has no flag that names a rules file
  (it has only --ignore-rules).
- codex-cli 0.163.0 lists a stable `hooks` feature. A pre-tool hook might be
  able to enforce an allow-list, but that is a different mechanism from the
  spec's rules file and was not tested.


Options for the Guildmaster (spec open question 1)
--------------------------------------------------

a. Accept sandbox-only limits for Codex review and judge profiles. This is a
   widening, and it needs an explicit decision.
b. Run those profiles in the read-only sandbox. Every command would still run
   with no allow-list, but nothing could write.
c. Wait for Codex to support deny-by-default.
d. Re-plan around a different enforcement mechanism, such as a Codex hook,
   once it has been spiked.
